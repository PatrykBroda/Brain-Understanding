# Synochi BJJ Coach

A personal Claude-wrapped BJJ + nervous-system coach that uses the user's own Obsidian vault ("SYNOCHI") as its knowledge base and builds an evolving, structured athlete model from every interaction.

Multi-user via Replit-managed Clerk (email+password + Google/Apple/GitHub SSO). Each Clerk user owns one fighter row; all data is partitioned by `users.clerkUserId` (FK `fighters.userId`). Signed-out users see the public `PublicLandingPage`; signed-in users see the FRAME home → onboarding (JIT) → app. The in-app sign-in/sign-up card headers are branded "FRAME" via the `<ClerkProvider localization>` prop in `artifacts/coach/src/App.tsx` (overrides `signIn.start`/`signUp.start` titles + subtitles, so they no longer show the Clerk tenant display name). The OAuth consent screen ("continue to <app name>" on Google's own page) still derives from the Clerk tenant display name — rename that in the workspace Auth pane.

## Architecture decisions

- **Two-layer prompt architecture.** Layer 1 (immutable philosophy: identity, posture, NEVER list, value priority, signal phrases) sits above Layer 2 (adaptive expression: register mirroring, banter default-on, sentence cadence). Named explicitly in the prompt so the model has a place to put each instruction — Layer 1 stays still while Layer 2 breathes. FRAME is the persona, SYNOCHI is the knowledge framework underneath. See `.agents/memory/frame-two-layer-architecture.md`.
- **No-fake-biometrics state.** The home orb label only ever shows interpretive words (Stable/Loaded/Recovering/Tight/Volatile/Composed/Overextended/Dormant) derived deterministically from real recorded `athlete_facts`. Never percentages, readiness scores, fatigue indices. Provenance is surfaced via `title=` tooltip. Restraint over engagement is a HARD product constraint — no streaks, no counters, no dopamine loops.
- **Analyse FRAME REPORT — honest numbers, the one principled exception.** The dividing line for the no-fake-numbers pillar is *fabrication*, not *numbers*. The shareable FRAME REPORT card shows AGGRESSION / COMPOSURE / REACTION SPEED / DEFENSIVE RECOVERY (0-100) and a composite SESSION SCORE (/100) because these are real: computed deterministically from on-device MediaPipe pose metrics in `analysis-metrics.ts`, each attribute carrying a `basis` provenance string surfaced in the card's score-provenance section. The **AI never emits numbers** — it writes only narrative (style profile name, grounded+hedged fighter parallels, personality comment, comparison note) and is told the numbers are fixed. `fragmentationRisk` stays categorical. The contract is enforced server-side, not trusted from the client: the route requires the four canonical score keys (`hasCanonicalScores`) and recomputes the headline SESSION SCORE itself (`recomputeSessionScore`, mirroring the client weighting) so a tampered payload can't fabricate the composite. Per-attribute values stay client-computed because pose runs on-device — an architectural reality, not a gap. The earlier-rejected "FRAME SCORE: 74" on Home is still rejected: there's no measured basis there. See `.agents/memory/no-fake-percentages-constraint.md`.
- **Vault baked into the build.** The full SPINE/IDENTITY/PROTOCOLS/Interaction Psychology/Guidance Dynamics layers are included verbatim; MODELS/MECHANISMS are a title+blurb index. ~100K tokens, sent as a single cached system block on every request.
- **System prompt = static (cached) + dynamic (per-fighter).** Static block has `cache_control: ephemeral`. Dynamic block injects fighter profile + all active facts grouped by category + recent calibration answers.
- **Conversation state lives server-side.** Frontend POSTs only the new `content`; the server loads full history from Postgres, calls Anthropic, persists the assistant reply.
- **Structured long-term memory in `athlete_facts`.** Categories: `strength | weakness | technical_knowledge | pattern | preference | event | goal | context`. Each fact has confidence (1-5), status (`active | superseded | resolved`), and source. Superseding preserves history; resolving marks a closed weakness/goal.
- **Memory writer runs after every assistant reply** as a separate Claude call (haiku, tool-use only — `add_fact` / `supersede_fact` / `resolve_fact`). Fire-and-forget: the user already got their reply; updates land before the next turn. Conservative system prompt: only durable observations, prefer supersede over duplicate.
- **Coach is told to anchor every technical claim** in the vault or the athlete's recorded model. Outside that, it names the gap and asks rather than fabricating.
- **Gauge → Match → Check pedagogy.** Before instructing on a new technical topic, the coach checks for a `technical_knowledge` fact on that topic; if none, it asks one short calibration question, then matches delivery depth to the recorded level. After a non-trivial concept it asks one short check.
- **Auth via Replit-managed Clerk.** Web app uses cookie session (no `Authorization` headers, no `getToken()` in browser code). Server: `clerkMiddleware(publishableKeyFromHost)` → `requireAuth` global on `/api/*` except `/healthz`. Client: `ClerkProvider` wraps app, `publishableKey = publishableKeyFromHost(window.location.hostname, VITE_CLERK_PUBLISHABLE_KEY)`, `proxyUrl = VITE_CLERK_PROXY_URL` (empty in dev, set in prod — do NOT gate on `PROD`). Tailwind v4: `@layer theme, base, clerk, components, utilities;` before `@import "tailwindcss"`, and `tailwindcss({ optimize: false })` in `vite.config.ts`. Sign-in/up styled via `clerkAppearance` (dark theme + FRAME variables).
- **One fighter per user.** `fighters.userId` is `unique notNull` referencing `users.clerkUserId` cascade. `getUserFighter()` JIT-creates the users row on first authed call so fresh sign-ups onboard cleanly. `insertFighterSchema` omits `userId` — the server injects it.
- **Drill prescriptions** as fenced ` ```drill ` JSON blocks; the frontend parses them into drill cards.
- **Calibration MCQs** surface after every 3 user messages; answers go into both `calibrations` AND `athlete_facts` (as low-confidence patterns) so they feed the next prompt.
- **Camp Mode (evolved from Competition Mode).** One organizing concept: the next fight. A fighter creates a Camp (event date / weigh-in / opponent / promotion / weight class / rounds / location / target+current weight / notes); only eventName+eventDate are required. When a camp is active (`eventDate >= startOfToday` — stays live through the whole event day), a tier-scaled red `CompetitionBanner` shows the countdown on Home + Chat, and a sternness directive is injected into the coach prompt that ramps base→build→sharpen→peak→fight_week as the date nears. The **Camp tab** (`/camp`) is the primary surface: a dashboard (countdown, phase Build/Develop/Sharpen/Fight Week, honest weight-cut readout), a manual training-session schedule (SESSION_TYPES sparring/wrestling/bjj/striking/conditioning/recovery/mobility) as the primary view, and the AI weekly mission as a secondary view. Training sessions live in `training_sessions` (campId+fighterId FK cascade, `source` manual|google_calendar). Server tier→phase collapse: base→Build, build→Develop, sharpen→Sharpen, peak+fight_week→Fight Week. Weight-cut is derived only from the real target/current difference — never a fabricated readiness score, and never subtracts across mismatched units (returns "Calibrating"). Google Calendar sync (import + confirm-before-write) goes through the Replit integration. No fake biometrics, no hype — pressure lives in the standard held, not in volume.
- **FRAME identity mythology.** The spirit-animal emblem is now a full combat-identity system sourced from the shared `lib/archetypes`. Each of the 10 animals is an archetype with a pressure signature / gift / shadow (shown on Profile as an "ARCHETYPE" block), injected into the coach's per-fighter prompt context (`archetypeLine` in `synochi.ts`). The belt ladder is reinterpreted psychologically (white=chaotic movement → black=stable under fragmentation) and rendered with its state + meaning under the belt (`belt.tsx`). `belt.tsx` draws a realistic prestige martial-arts belt (crossing bands + centre knot + hanging tails + gold edge stitching + rank tip bar + golden halo, restrained reduced-motion-guarded gold micro-animations) plus an 8-rung aspirational progression ladder (white/yellow/orange/green/blue/purple/brown/black — only earned rungs lit, current pulses; the ladder spans all combat sports even though `BELT_PSYCHOLOGY` only defines the 5 BJJ keys, so yellow/orange/green live as dormant future rungs in `belt.tsx`'s local `LADDER`). The ladder carries a single `role="img"` aria summary; per-rung decoration is `aria-hidden`. Profile wraps the belt in a "FRAME RANK" dashboard card (header + Belt + 3-col meta grid Integrity/Cadence/Days-in-frame, folding in the former standalone frame-integrity bar — built from real data only, no fabricated progress %, streak, or days-active despite the reference mockup asking for them). `belt.tsx` keeps its public API (`Belt({level,showMeaning})` + `beltKey` export → `frame-report-card.tsx`/`onboarding.tsx` unaffected). "Frame integrity" keeps its categorical label + segmented bar but now carries a one-line plain-English definition ("how much of your structure survives when pressure spikes — composure under fragmentation, not a fitness score"). The user floated a numeric "FRAME SCORE: 74" — deliberately NOT built; it violates the hard no-fake-percentages pillar. Intent honored via punchier interpretive language instead.
- **DOB is the single source of truth for age.** The client never writes `age` — both `insertFighterSchema` and `updateFighterSchema` OMIT it. The server recomputes `age` from `dateOfBirth` (`ageFromDob`, UTC) on every POST/PATCH and rejects an invalid/missing DOB. `insert` requires DOB; `PATCH` only recomputes when DOB is in the patch. A duplicate client-side `ageFromDob` in `fighter-options.ts` (local time) drives the live "N years old" hint in onboarding + profile-edit; the server copy is authoritative. This keeps the two values from ever desyncing (the no-fake-numbers pillar applied to derived data).
- **All combat sports, not BJJ-only.** `fighters.primarySport` (mma/boxing/muay_thai/kickboxing/bjj/wrestling/judo/karate/mixed) feeds a `sportBlock` reframe in `synochi.ts` so FRAME presents as an adaptive combat-performance OS that speaks the athlete's sport's language. The vault stays BJJ-rich but is framed as one expression of the underlying system.
- **Interactive breathing protocols.** The coach prescribes regulation via fenced ` ```breath ` JSON blocks (parallel to ` ```drill `), parsed in `message-content.tsx` into a `BreathCard`. The card runs a guided session: an octagon that expands on inhale and contracts on exhale, a per-phase countdown (inhale/holdIn/exhale/holdOut, zero-length phases skipped), round tracking, and Begin/Pause/Resume/Reset. No fake biometrics — it's a timer, not a measurement.
- **3-layer glossary.** `glossary.ts` entries are `{ quick, why?, train? }`. The popover surfaces them progressively: quick definition always, "Why it matters" reveal if `why`, "Train this →" if `train` (sends the prompt back into chat via `TrainContext`). Only curated terms get the dotted-underline `.glossable` affordance — deterministic, nothing else looks tappable.
- **Coaching depth (prompt + UI).** (1) Tap-to-simplify: heavy terms in coach replies are dotted-underline tappable, opening a one-line plain-English gloss from a curated `lib/glossary.ts` (deterministic — only terms we have a real definition for). (2) Vocabulary growth: `computeVocabulary` term-density tier (see vocabulary.ts) rises with recorded technical knowledge and steers prompt language density; shown on Profile as "Tier N/5" + "Concepts held". (3) Sharper first-contact: the welcome briefing branches on real conversation history (`!last`, NOT fact count) into a funnier archetype read that refuses to fake deep knowledge. (4) `synochi.ts` prompt has explicit "Adaptive friction scaling" (how hard to push is a dial set by state/model, not mood) and "Frame integrity" (protect structural composure; one load-bearing fix at a time) sections.
- **Coaching mode = same system, different coach.** `computeCoachingMode` (shared `lib/archetypes`) derives one of Explorer/Builder/Competitor/Performer from REAL data only (scheduled competition → advanced level → intermediate-or-model≥8 → explorer) and is the single source of truth for BOTH the coach prompt (a friction-posture block in `buildDynamicContext`, so welcome + chat both get it) and the Profile Athlete State panel. It's a posture dial layered on top of (not replacing) adaptive friction scaling + the competition tier; the model is told never to announce the mode.
- **Time-aware chat re-entry.** The welcome route tiers by gap since the athlete's last message: `<2h` silent, `[2h,24h)` returning, `[24h,72h]` new-day, `>72h` lapsed (boundaries inclusive on the stale + new-day gates). HARD honesty constraint: the lapsed directive must never claim the athlete hasn't TRAINED N days — we only know FRAME silence, so it phrases the gap strictly as "away from the frame", then asks. First-contact is keyed on `!last`, never fact count.

## Product

Mobile-first 3-tab app (will be wrapped in a mobile shell). All routes gated by `useFighter()`; first-run shows onboarding.

1. **Onboarding** — cinematic multi-step behavioral calibration ("Let's see what you become under pressure"): name → 4 MCQs about behaviour under load (fatigue / imposed pace / proudest win / chaos) → practical details (age, art, level, frequency, goals, weaknesses, competes). Each MCQ answer carries a short "read" sentence; the answers are composed into the `personality` string that drives server-side archetype assignment. Seeds the model. Progress bar, auto-advance, Back nav, "Reading you…" submit.
2. **Landing hub (`/`)** — minimalist boot screen: FRAME / CALIBRATION SYSTEM wordmark, profile shortcut (shield icon), biological CosmicOrb centered, interpretive STATE label (Dormant/Stable/Loaded/Recovering/Tight/Volatile/Composed/Overextended, derived honestly from recorded facts, tooltip shows source), ONE deterministic cue line from a `STATE_CUE: Record<FrameStateLabel,string>` map, a readiness line (today's check-in composite "· today" else latest analysis sessionScore "· last session" else an honest "Analyse a session" prompt; links to /home or /analyse accordingly), Continue CTA → `/chat`, bottom nav. ## Gotchas

- After editing the vault content under `artifacts/api-server/src/synochi/`, the prebuild script regenerates `synochi.generated.ts` automatically on next `dev`/`build`.
- Composite libs (`lib/db`) emit `.d.ts` — after schema changes, `pnpm run typecheck:libs` (or `pnpm run typecheck`) before checking artifact typecheck.
- Smoke suites run fully isolated AND always fresh: `scripts/run-{coach,mobile}-smoke.sh` start their own API + frontend on RANDOMIZED per-run ports (coach 18100-18899, mobile 19100-19899) behind `scripts/smoke-proxy.mjs` and set `SMOKE_BASE_URL` for Playwright — they never touch main workflow ports, never reuse a stale server from a previous run (survivors are killed via /tmp/{coach,mobile}-smoke.pids), and readiness is HTTP-based (pid1 forward-listens and answers 502, so raw TCP is not a valid up-signal). The mobile runner also gates on bundle freshness: if any frame-mobile source file is newer than `dist/index.html` it rebuilds automatically (fails loudly on build failure) and prints whether dist/ was REBUILT or CONFIRMED CURRENT.
- Do NOT re-add a `postbuild` (or any) test hook to `artifacts/api-server`'s build path. Tests must not run on the dev/prod BUILD — it slowed every boot (~12s) and let the smoke workflows race port 8080 → `EADDRINUSE` → server never came up → app 502'd on login + every feature. Prod deploys are therefore NOT test-gated by the build; tests run via the dedicated `test` / `api-server-tests` workflows + validation instead. `index.ts` retries `EADDRINUSE` (10×1s) via `server.on("error")` so a restart that overlaps the old instance's port release recovers instead of crashing (the old `app.listen(port,(err)=>…)` callback was dead code — that arg is never an error). See `.agents/memory/api-server-boot-reliability.md`.
- Streaming endpoint is `POST /api/coach/chat` with body `{ content: string }` and returns SSE `data: {content|done|error}` events. Client (`use-chat.ts`) guards the stream with an AbortController watchdog (60s for first token, 30s idle once flowing); a stream that closes WITHOUT a `{done:true}` event, or sends `{error}`, is treated as a failure (in-character message + Retry button), and the empty pending "sensing" bubble is cleared so it never hangs. `retry()` re-sends the last attempt; the server reuses an immediately-preceding identical unanswered user row (text-only turns, ordered `createdAt DESC, id DESC`) so retry doesn't duplicate history. Known minor edge: if a turn streams PARTIAL text then drops, the server persists that partial assistant reply (its catch block) and retry can't safely auto-delete it (can't distinguish a failed partial from a completed reply by content alone), so the partial stays in history. Per-turn vault retrieval is 6 nodes (was 8) to shrink the uncached dynamic block for faster first token; Claude usage (`cache_read/creation_input_tokens`) is logged per turn to confirm prompt caching is hot.
- Drill blocks must be valid JSON inside ` ```drill ... ``` ` fences — the parser silently skips invalid ones. Breath blocks work identically inside ` ```breath ... ``` ` fences (fields: `title`, `purpose`, `inhale`, `holdIn`, `exhale`, `holdOut`, `rounds`, `note` — seconds clamped 0-30, zero-length phases skipped).
- Memory extraction runs ~3-12s after stream end. Frontend invalidates the `memory` query 1.5s after `isStreaming` flips off; opening the panel sooner just shows the previous state.
- `athlete_signals` table still exists for back-compat but is no longer written to; all new memory goes into `athlete_facts`.
- Clerk auth: do not add NODE_ENV/PROD gates around `proxyUrl` or `publishableKey`; do not hard-code the proxy path; do not use `<UserButton>` (skill forbids it — we have a custom Sign out button on Profile). Sign-in/up routes must be `path="/sign-in/*?"` and `"/sign-up/*?"` verbatim (the `/*?` wildcard catches OAuth callbacks). DB was wiped during the auth migration (no per-user backfill of prior singleton data).
- Clerk dev 401 / all-null `getAuth` (every `/api/*` returns 401 while the browser thinks it's signed in) is a DEV BROWSER-STATE issue, not a server bug — config is canonical. Two causes compound: (1) long-lived `*.replit.dev` dev domains accumulate duplicate Clerk cookies, with a STALE parent-domain (`.replit.dev`) `__session`/`__session_<suffix>` shadowing the fresh subdomain copy; (2) dev does NOT proxy Clerk, so FAPI is third-party — incognito blocks third-party cookies, so incognito sign-in fails in dev and is NOT a valid test (prod proxies Clerk first-party and is unaffected). Fix: clear all `replit.dev` cookies / use a fresh non-incognito browser, then sign in. Do not hack Clerk cookie reading. See `.agents/memory/clerk-dev-cookie-pollution.md`.
- Clerk "Too many requests" (HTTP 429) on `POST /api/__clerk/v1/client/sign_ups` in the PUBLISHED app = the production deployment is still effectively on DEV (test) Clerk keys, whose strict usage caps real athletes hit. Signature: a sign-up succeeds, then a later one fast-rejects with 429 (dev-instance cap, not rapid-retry). The auth code is canonical — NOT a code bug, do not edit/rotate keys or bump `@clerk/*`. Fix is operational: RE-PUBLISH so live `pk_live`/`sk_live` keys bake into the build; verify in Publishing → Overview → Adjust settings that prod `CLERK_PUBLISHABLE_KEY`/`CLERK_SECRET_KEY` are `pk_live`/`sk_live`. Live keys have no MAU limit. See `.agents/memory/clerk-prod-rate-limit.md`.
- Planner keys weeks by `isoMondayUTC()` (Monday 00:00 UTC). One plan per fighter per week; regenerate wipes existing completions because new item keys won't match. Completing an item writes a `pattern` fact with `source = "planner:item:<key>"` (confidence 2); un-completing resolves any planner-sourced facts for that key. Generator routes through the active conversation's `aiProvider` (Claude → tool_use, OpenAI → response_format json_object). Validation refuses any plan that has items without a real fact id / calibration key, fewer than 5 items, or fewer than 3 distinct categories — retries once before erroring.
